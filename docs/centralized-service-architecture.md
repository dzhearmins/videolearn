## 0. 结论先行

1. **你的设想技术上成立，但它是四个候选方案里唯一"两头不讨好"的组合。**
   把 PKU 密码放到服务器上，就继承了方案 A（全服务端）的全部爆炸半径；
   把 ASR 放到用户电脑上，又继承了方案 B（本机 worker）的全部安装摩擦。
   你付出了 A 的风险 + B 的成本，换来的只有"服务器省 CPU"这一项。
   而这一项在§3 的容量测算里，是**峰值问题，不是均值问题**，有更便宜的解法。

2. **"网页对外"不等于"中心服务器"。** 如果目的只是"同学不用装 Python、不用我远程帮他们跑"，
   方案 C（本地 Web UI：`videolearn web` → 浏览器开 127.0.0.1）用 1–2 周就能达到同样的体验，
   而服务器端一个字节的凭据都不需要。**这是性价比最高的一步，建议先做。**
   若还想让同班共享"已跑过的总结"，只需给 C 加一个只存文字的缓存服务
   （[shared-summary-cache.md](shared-summary-cache.md)），不改变零凭据属性。

3. 如果目的确实是"多设备、共享、远程排队"，做 **方案 B：控制面 + 本机 worker**。
   服务端只管账户、任务、LLM 调用、文本产物；PKU 密码和媒体永远不离开用户机器。

4. 如果只在一个 ≤20 人的可信小圈子里用，且大家知情同意，方案 A（全服务端）在技术上是四条路里
   最简单、体验最好的；**代价是把"运营一个代登录服务"这件事本身接下来**（§2）。

5. **决定架构顺序应该是：先决定"PKU 密码放哪"，再决定"ASR 放哪"。**
   前者不可逆（泄露无法撤回），后者可替换（§3.4 的接缝只有一行函数签名）。

6. 开工前必须先跑三个实测（§11 Phase 0），其中任意一个为否，方案 A/D 直接出局。

## 1. 把问题拆对：五个可以独立决定的维度

当前代码把这五件事焊死在"一个进程 + 一个 `.env` + 一个 `output/` 目录"里。
中心化的本质，就是把这五个维度分别拆出来、各自决定归属。

| 维度 | 现在怎么做的 | 代码位置 | 拆开后的选项 |
|---|---|---|---|
| 身份与凭据 | 进程级单例：`PKU_STUDENT_ID/PASSWORD` 从 `.env` 读，Cookie 写固定路径 | `config.py` / `session.py` / `iaaa.py` | 用户本机 / 服务器托管 / 本地登录后上传 Cookie |
| 媒体获取 | 与登录同一个 `requests.Session` 下载 HLS | `media.py` / `blackboard.py` | 用户本机 / 服务器 / 服务器只转音频 |
| 语音识别 | 进程内 faster-whisper，CPU int8，`cpu_threads=8` | `asr.py` / `streaming.py` | 用户本机 / 服务器 CPU / 服务器 GPU |
| LLM 调用 | 单一 `DEEPSEEK_API_KEY`，全局 | `config.py` / `llm.py` | 每用户自带 key / 平台统一 key |
| 产物 | 本地路径 `output/课程名/时间_标题/`，`print()` 进度 | `pipeline.py` / `cli.py` | 本地 / 对象存储 / 两者同步 |

**关键观察：这五个维度里，只有第一个（密码）是不可逆的。**
其余四个都可以在后期替换而不改变产品形态。所以论证的重心必须放在密码上。

## 2. 论证一：PKU 密码该不该上服务器

### 2.1 现在为什么安全

单人 CLI 下，密码的爆炸半径 = 1 个账号、1 台机器。`.env` 被 gitignore，
`.state/cookies.json` 只存在于本机，日志只输出"已设置/未设置"。这是正确的。

### 2.2 上服务器意味着什么

服务器一旦要"用户填一次密码、以后自动跑"，就必须**长期保存可解密的口令**，
因为 Cookie 会过期、需要自动重登。于是：

- **爆炸半径从 1 变成 N。** 一次数据库泄露/备份泄露/内鬼/运维误操作 = 全站 PKU 账号。
- **服务器成为"凭据预言机"。** 任何拿到站点账户的人都能拿它批量试学号密码是否有效
  —— 这比泄露更糟：它让服务本身变成攻击工具。
- **信任悖论。** 一个第三方网站让用户输入北大统一身份认证密码，形态上和钓鱼完全一致。
  学校的安全宣传一直在教学生"不要在任何非 pku.edu.cn 的页面输入学号密码"。
  做这个产品等于要求学生违反自己受过的安全训练；一旦有人举报，你很难自证清白。**这一条与技术无关，但可能是最致命的一条。**
- **合规问题。** 学号+密码属于《个人信息保护法》下的敏感个人信息，托管他人密码需要
  单独同意、明确告知处理目的/方式/期限、最小必要、加密存储、泄露通知、删除机制。
  "用户自己填进来的"不等于"可以随便存"。
- **学校侧的定性。** 教学网统一身份认证通常不允许把凭据交给第三方系统；一个集中代登录的
  服务在风控视角下是"异常登录源"，可能连累用户账号被标记。这条我无法替你确认，
  但它是**运营层面的真实风险**，不是技术洁癖。
- **日志与内存。** 加解密一次，明文就会经过 request body、进程内存、异常栈、崩溃转储、
  反向代理 access log。任何一处没脱敏就是全站泄露。

### 2.3 三个被低估的技术约束

这三条比"安全"更硬，因为它们会直接让功能不可用：

1. **手机令牌 / OTP。** `iaaa.py` 的请求体里有 `smsCode`、`otpCode`，错误码 `E05` 是
   "手机令牌验证码错误"。开了二次验证的账号**无法无人值守登录**。
   服务端模式要么要求用户每次提供 OTP（那就不能后台自动跑），要么排除这批用户。
2. **`E21` 账户锁定。** 登录失败次数过多锁定 30 分钟。集中登录意味着所有用户共享
   一个出口 IP、一段自动重试逻辑；一个 bug、一次批量重连，就可能把**一批**账号打到锁定。
   而本机登录天然是"每个人自己的 IP、自己的节奏"，与正常使用一致。
3. **会话/IP 绑定（待验证）。** HLS 的 AES-128 key 是用**同一个会话**去取的
   （`media._get_key`）。如果 key 或 Cookie 绑定了 IP/UA 指纹，那么"用户在 A 地登录、
   服务器在 B 地下载"会直接 403。这一条必须在 Phase 0 实测（§11）。

### 2.4 如果坚持要让服务器登录：最低安全线

不是不能做，但下面每一条都不是可选项：

- 明文口令**只在登录瞬间存在于内存**，登录后立即清零，不落盘、不入日志、不进异常信息；
- Cookie 单独加密存储，短 TTL、可单条撤销、可"退出所有设备"；
- 站点强制 HTTPS + HSTS；站点口令用 argon2id；管理员强制 2FA；
- 关闭崩溃转储；反向代理只记 method/path/status，不记 body/query；
- 每个用户可"立即删除我的凭据"；保留期写明（如 30 天）；
- 白名单内测（邀请码），不做公开注册；
- 审计：谁在何时用谁的凭据登录，只记事件不记内容。

做到这些，也只是把风险降到"可信小圈子"可接受的程度，**不改变"服务器可以代替任何人登录"这个事实**。

## 3. 论证二：ASR 放在哪里

### 3.1 先说实测数字（有出处）

| 指标 | 实测值 | 出处 |
|---|---|---|
| 课程时长 | 7162.4 s | `output/.../stream_bench.md` |
| ASR 纯耗时（base, int8, 8 线程） | 295.0 s → **24.3× 实时** | 同上 |
| 流式总耗时 / 视频时长 | 297.6 / 7162.4 = 4.2% | 同上 |
| 峰值 RSS | 0.53 GB | 同上 |
| 视频体积 | 1038.1 MB（2 h） | 本机文件 |
| 本机 CPU | i7-13700H，14 核 20 线程，无独显 | 本机 |

注意 README 里"29 秒音频用 18 秒（0.6× 实时）"那个数字**不能用来估算长音频**：
29 秒的样本里，模型加载和首块预热很可能占了大部分时间。长音频的稳态吞吐是 15–24× 实时（base）；
同样能佐证的细节是：120 s 样本 7.5 s（16×）比 7162 s 的 24.3× 慢，正是短块固定开销占比更高。
`small` 的实测补充（2026-11-18，Web UI 端到端跑通时的真实小样）：90 s 音频、8 线程、**含模型加载**，
ASR 28.2 s ≈ **3.2× 实时**；扣掉加载按稳态 ~4.5× 估，两小时课约 27 分钟。
原先按 6–8× 的估计偏乐观，§3.2/§10 的数字因此偏小约 1.3–1.8 倍，但"均值够、峰值不够"的结论不变。

### 3.2 服务端容量的真实瓶颈是"峰值"，不是"均值"

按 100 个用户、每人每周 2 节课、每节 2 h 估算：

- 音频总量：100 × 2 × 7200 s = 144 万秒/周。
- `small` @ 6× 实时、8 线程：单课墙钟 1200 s，CPU 占用 1200 × 8 = 9600 CPU·秒 ≈ **2.7 CPU·小时**。
- 每周总量：200 课 × 2.7 ≈ **540 CPU·小时/周**。
- 一台 16 vCPU 独占机器供给 16 × 168 = 2688 CPU·小时/周 → **平均利用率约 20%**。

所以"服务器跑不动"是错的。真正的问题是：

- **峰值。** 大家下课之后集中提交。周日晚 4 小时内来 100 节课，需要在 4 小时里提供
  270 CPU·小时 → **约 68 vCPU**。要么排队（用户等 1–3 小时，直接毁掉"边转写边出稿"这个卖点），
  要么弹性扩容（贵，且冷启动要拉模型）。
- **线程争用。** `streaming.py` 里 `WhisperModel(..., cpu_threads=threads)` 是硬编码 8，
  两个任务并发就把 16 vCPU 打满，三个开始互相拖慢。要做多租户必须改成配额/池化 +
  模型常驻复用（现在每个任务都新建 `WhisperModel`，有固定加载开销）。
- **单点故障。** 服务器挂了，所有人一起停。本机 ASR 下，服务器挂了只影响"出稿"。

结论：**服务端 ASR 在均值上完全可行，在峰值上要付 3–5 倍的钱和一堆运维复杂度。**

> 按实测 4.5× 重算的敏感度：单课约 3.6 CPU·h，200 课/周 ≈ 720 CPU·h，
> 16 vCPU 均值约 27%，周日晚 4 小时峰值约 90 vCPU。结论不变，只是更贵。

### 3.3 本机 ASR 的代价（要诚实）

- 用户要装东西。但注意：**现在的产品已经要求 Python + ffmpeg**，普通同学本来就要人帮。
  真正的问题不是"要不要装"，而是"能不能装明白"。
- 模型首次下载 0.5 GB（`small` int8），国内网络要走 `HF_ENDPOINT` 镜像。
- 一台 4 核笔记本跑 2 h 课约 30–40 分钟，风扇狂转、不能休眠。
- 断网/合盖/休眠 = 任务中断，必须有断点续传（现在的 `transcript.partial.md` 只落盘，**不能续跑**，
  崩溃后从第 0 块重来）。
- 音频不出本机，这是隐私上的实打实的好处。

### 3.4 但接缝非常窄，这是本机 ASR 可行的根本原因

`streaming.py` 里真正跨机器的边界只有一条：

```python
audio = decode_chunk(video_path, chunk_start, take, ffmpeg)   # 240s → float32 PCM
segs, _ = wm.transcribe(audio, language="zh", beam_size=1, vad_filter=True, ...)
```

分块、重叠 5 s、首句去重、`queue(maxsize=1)` 背压、LLM 流式消费——**全都不需要动**。
把 `wm.transcribe` 换成一个 `AsrBackend` 实现即可（本地实现 = 现有 faster-whisper；
远程实现 = WSS/HTTP 把 PCM 发给用户机器）。参见附录 A。

这意味着：**"本机 ASR"不是重写，是注入。** 这一点让方案 B/D 的工程风险远低于直觉。

### 3.5 结论

- 本机 ASR 可行、与现有流式架构兼容、改造量小；
- 它的收益是"零边际成本 + 峰值免费 + 音频不出本机"，**不是"服务器做不到"**；
- 它的代价是安装摩擦与中断恢复，这两件事必须用产品手段解决（一键包 + 断点续传），
  否则用户会在第一次失败后流失。

## 4. 论证三：媒体和产物放在哪里

### 4.1 体积

| 形态 | 2 h 课程体积 | 说明 |
|---|---|---|
| 原始视频 | **1.04 GB** | 实测 7162 s → 1038 MB，约 1.16 Mbps |
| 音频（AAC 64k） | 58 MB | |
| 音频（Opus 32k） | 29 MB | 语音识别足够 |
| PCM f32 16 kHz | 460 MB | 只在内存/管道里出现，不该落盘 |
| 文本产物 | 约 30 KB | `transcript.md` ≈ 1.1 万字 |
| 截图 8–20 张 | 1–3 MB | 1280px JPEG |

### 4.2 网络与 IP

- `course.pku.edu.cn` 公网可达（`doctor` 会测）；但 `yjapise.pku.edu.cn` 的媒体接口
  是否限制校园网/IP，**必须实测**。如果限制，服务端下载直接不可行，方案 A/D 出局。
- 即使可达，200 课/周 × 1.04 GB = **208 GB/周入站**，滚动保留一周就是 200 GB 存储。
  这不是钱的问题，是"你为什么要在服务器上囤 200 GB 别人的课堂录像"的问题。
- HLS 的 AES-128 key 用同一会话取（`media._get_key`），若 key 绑定会话/IP，
  跨机器下载会失败——这是 §2.3 第 3 条的同一件事。

### 4.3 合规

- 视频画面本身带"未经授权不得翻录转载"的版权提示。个人自用是一回事；
  **运营一个替别人下载、并在服务器上缓存的公开服务是另一回事**，性质接近"提供复制/传播工具"。
- 建议：**服务端永远不落视频**。如果必须服务端下载（A/D），只保留音频、任务结束立即删除，
  并把这个策略写进用户协议。

### 4.4 结论

媒体留在用户侧（方案 B/C）同时解决三个问题：带宽账单、IP 限制、版权定性。
**这是本机 worker 相对"服务端下载 + 本机识别"的第二个隐藏优势**——后者（D）仍然要服务器下载 1 GB/课。

## 5. 四个候选架构

### A. 全服务端（最简单，风险最高）

```
浏览器 ──HTTPS──> 服务端 ──登录/下载/ASR/LLM──> 存储 ──> 浏览器
                 （持有全部用户密码）
```

- 优点：用户体验最好（填完什么都不用管），实现最接近现有代码（`pipeline.run_for_video` 直接跑）。
- 缺点：凭据托管、208 GB/周入站、1 TB 级存储、峰值要 68 vCPU、版权定性最差。

### B. 控制面 + 本机 worker（推荐的多用户形态）

```
浏览器 ──HTTPS/SSE──> 控制面（账户/任务/LLM/文本产物）
                          ⇅ WSS 长连接（设备令牌 + 单任务令牌）
                    本机 worker（登录/下载/ASR/抽帧）
```

- 优点：密码与媒体不出本机；峰值成本为 0；服务端最坏泄露只有站点口令和文字稿；
  版权上服务器不存视频。
- 缺点：要装 worker；要做双端排障；眼睛阶段要跨机器编排。

### C. 本地 Web UI（"网页"但不"中心化"）

```
浏览器 ──> 127.0.0.1:xxxx（原 CLI + Web 前端，打包成 exe）
```

- 优点：零凭据风险、零服务器成本、改动最小（把 `cli.py` 的交互换成 HTTP 路由）。
- 缺点：没有跨设备、没有共享、没有远程排队；每个人一个孤立实例。
- **这是"同学不用配环境"这个诉求的正确答案**，而很多人会误以为它需要中心服务器。
- 可选的增量：一个只存文字的"共享总结缓存"服务器（同班有人跑过就直接复制），
  它不改变零凭据属性，见 [shared-summary-cache.md](shared-summary-cache.md)。

### D. 混合（你的设想：网页收密码 + 本机 ASR）

```
浏览器 ──HTTPS──> 控制面（密码/登录/下载/转码）
                       │ 下发音频块（PCM/Opus）
                 本机 ASR worker ──> 文本回传
```

- 优点：服务器省 CPU；worker 很薄（只需要 whisper，不需要懂 PKU 的 Cookie/HLS）。
- 缺点：见§6。

### 对比表

| | A 全服务端 | B 控制面+worker | C 本地 Web UI | D 混合（你的设想） |
|---|---|---|---|---|
| PKU 密码在哪 | **服务器** | 用户机器 | 用户机器 | **服务器** |
| 媒体从哪下载 | 服务器 | 用户机器 | 用户机器 | 服务器 |
| ASR 在哪 | 服务器 | 用户机器 | 用户机器 | 用户机器 |
| 用户要装东西 | 否 | 是（worker） | 是（一键包） | 是（worker） |
| 服务端最坏泄露 | 全站 PKU 账号 | 站点口令 + 文字稿 | 无 | 全站 PKU 账号 |
| 峰值算力成本 | 高 | 0 | 0 | 下载带宽高 |
| 断线影响 | 无 | 任务暂停可续 | 本机任务失败 | 任务失败 |
| 工程量（相对 C） | 中 | 大 | 小 | 中大 |
| 适合 | ≤20 人可信圈 | 多用户公开 | 个人/小圈子 | 明确接受凭据风险时的省钱版 |

## 6. 为什么 D 是最差组合（专章）

把 D 分别和 A、B 对比，结论就很清楚。

**D vs A（风险相同，复杂度更高）**
- 两者都让服务器持有全部密码，爆炸半径一样；D 还多出：音频传输协议、worker 版本协商、
  断线重连、双端日志、跨机器超时。**同样的风险，更多的零件。**
- 唯一的收益是"ASR 的 CPU 不算在服务器账上"。但§3.2 已经说明：均值只要 20% 利用率，
  峰值可以用队列或弹性解决。**用凭据风险去换一项"均值本来就不紧张"的资源，不划算。**

**D vs B（安装成本相同，隔离收益为零）**
- 两者都要求用户装 worker；B 的 worker 顺便把登录和下载也做了，于是服务器什么都不用碰。
- D 的 worker 虽然薄，但正因为薄，它**没有解决任何真正难的问题**：
  用户还是要装、要连、要排障，而最危险的那一步仍然发生在服务器上。
- 一句话：**既然都要装，为什么不把最脏的活一起放到本机。**

**D 唯一成立的条件**（如果确有这些条件，D 可以做）：
1. 用户数 ≤ 数十人，全部知情同意，且你能承担"服务器可代所有人登录"的后果；
2. 你确实没有 GPU/预算，且明确要用用户 CPU 顶峰值；
3. 你接受"服务器仍然要下载 1 GB/课、仍然要处理版权内容"；
4. 你实现了§2.4 的全部最低安全线。

**变体 E（值得知道，但别选）**：用户在本地登录，只把**短期 Cookie** 上传给服务器，
服务器用 Cookie 下载+识别。密码不落服务器，但 Cookie 是 bearer token，
在有效期内等价于账号权限，且很可能绑 IP（§2.3 第 3 条）。它只适合
"服务端下载确有必要、且只在内网"的场景。

### 6.1 若你确认要走 D：最小可行形态

尊重你的选择——如果上面 4 个条件你都接受，D 可以按下面这个最小形态落地，
它的工程量大约是 B 的 1/2，因为 worker 端不需要懂 PKU：

1. **服务端**：完全复用现有 `pipeline.run_for_video`，只把 `streaming.run_streaming`
   里的 `WhisperModel` 换成 `RemoteWhisper(channel)`（附录 A.1）。
   下载、分块、LLM、眼睛全部照旧。
2. **传输**：不要把 f32 PCM 直接发（240 s = 15.4 MB，约 0.5 Mbps 持续）。
   服务端用现成的 ffmpeg 转 Opus 32 kbps（240 s ≈ 0.96 MB，降 16 倍），
   worker 端用 ffmpeg 解回 16 kHz f32——ffmpeg 在两端本来就有。
3. **worker**：约 200 行——WSS 连上、收 `pcm`、跑 `LocalWhisper`、回 `segments`、心跳。
   不做登录、不做下载、不做抽帧（眼睛仍在服务端做，因为视频在服务端）。
4. **必须具备**：设备令牌、单任务 capability、断线重连、块级幂等、worker 掉线时任务暂停。
5. **仍然必须做**：§2.4 全部、§8 的三个并发 bug 修复、§4.3 的"不落视频"。

这个形态下 D 的真实成本是：**每课 1 GB 入站 + 200 GB 级存储 + 凭据托管**，
换来的是"你的服务器不用买 CPU"。如果你算过账觉得值，那就做；
但请把§2.4 的清单当成验收项，而不是建议项。

## 7. 推荐架构 B 的设计要点

### 7.1 组件

```
┌─────────────┐   HTTPS + SSE   ┌──────────────────────────────┐
│  浏览器 SPA  │ ──────────────> │  API 服务（FastAPI/asyncio） │
└─────────────┘                 │  ├ 账户与会话                │
                                │  ├ 任务编排（状态机）        │
                                │  ├ LLM 网关（用户 key）      │
                                │  ├ SSE 事件总线              │
                                │  └ 产物签名 URL              │
                                └───────┬──────────────┬───────┘
                                        │              │
                              WSS（设备令牌）     对象存储/DB
                                        │         （只存文本/截图）
                                ┌───────┴────────────────┐
                                │ 本机 worker            │
                                │ ├ IAAA 登录（本地）    │
                                │ ├ 课程/回放列表        │
                                │ ├ HLS 下载 + ffmpeg    │
                                │ ├ faster-whisper       │
                                │ └ 抽帧（眼睛）         │
                                └────────────────────────┘
```

**原则：服务端不碰 PKU 的 Cookie、play_url、视频、音频；worker 不碰其他用户的数据。**

### 7.2 一次任务的时序

```
用户        浏览器          API               worker
 │  选课/发起   │              │                  │
 │────────────>│  POST /jobs  │                  │
 │             │─────────────>│ 建 job(queued)   │
 │             │  SSE 订阅    │                  │
 │             │<────────────>│                  │
 │             │              │── WSS job.new ──>│ 领取（lease 60s）
 │             │              │<── accepted ─────│
 │             │              │                  │ 列回放→解析 play_url
 │             │              │                  │ 下载→解码→ASR
 │             │              │<── chunk #0 ─────│ 转写第 0 块
 │             │              │ LLM 流式初稿     │
 │             │<── draft.delta│                  │
 │             │              │<── chunk #1 ─────│
 │             │              │ ...              │
 │             │              │<── frames? ──────│ 眼睛取帧（JPEG 上传）
 │             │              │ final_pass       │
 │             │<── done ─────│                  │ 任务结束，本地清理
```

### 7.3 状态机与断点续传

```
queued → leased → downloading → transcribing → eyes → finalizing → done
             ↘ failed / canceled（任意状态可进入）
```

- `lease` 60 s，worker 每 10 s 心跳；3 次未心跳 → 任务回到 `queued`（标记 `needs_worker`）。
- **chunk 幂等**：`(job_id, idx)` 唯一键，重复上传覆盖而不追加。
  恢复时 `SELECT max(idx)`，从下一块继续。这是现在 `transcript.partial.md` 想做但没做到的事。
- 服务端维护 `transcript.md` 为 chunk 的物化视图（按 idx 排序拼接），
  这样"边转写边出稿"在服务端也能成立，且天然支持重跑 final_pass（不需要重新 ASR）。

### 7.4 接口草图

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/session` | 站点登录（argon2id + 可选 TOTP） |
| PUT | `/api/llm-key` | 保存用户 key（AES-GCM 加密，返回 `sk-…abcd`） |
| POST | `/api/devices/pair` | 生成 6 位配对码，worker 用它换设备令牌 |
| GET | `/api/lectures` | 课程/回放列表（由 worker 上报的元数据） |
| POST | `/api/jobs` | 创建任务（lecture_id + 参数） |
| GET | `/api/jobs/{id}/events` | SSE：`state`/`chunk`/`draft.delta`/`frame`/`error`/`done` |
| POST | `/api/worker/lease` | worker 领取任务（WSS 不可用时的回退：长轮询 25 s） |
| POST | `/api/worker/jobs/{id}/chunks` | 上传转写块（幂等） |
| POST | `/api/worker/jobs/{id}/frames` | 上传截图（JPEG ≤ 200 KB/张） |
| POST | `/api/worker/jobs/{id}/complete` | 完成/失败 |

鉴权三层：浏览器用 HttpOnly Cookie 会话；worker 用设备令牌（可撤销）；
单任务用 capability JWT（`job_id + user_id`，30 分钟过期，不能访问别的 job）。

### 7.5 数据模型（最小集）

```sql
users(id, email, pwd_hash, status, created_at)
llm_credentials(user_id, ciphertext, nonce, key_version, last4, updated_at)
devices(id, user_id, name, token_hash, last_seen, revoked_at)
courses(id, user_id, pku_key, name, term)
lectures(id, course_id, title, record_time, duration_sec, pku_ref)
jobs(id, user_id, lecture_id, state, params_json, progress, error, created_at, finished_at)
chunks(job_id, idx, start_sec, end_sec, text, chars, PRIMARY KEY(job_id, idx))
frames(job_id, seq, t_sec, path, bytes)
artifacts(job_id, kind, path, bytes, sha256)
events(id, job_id, ts, kind, payload_json)   -- 审计 + 进度回放
```

注意两点：
- **不存 `play_url`**（JWT 短期有效）。存 `pku_ref`（课程 key + 录制时间 + 标题），
  任务开始时由 worker 重新解析。
- 产物路径用 `{user_id}/{job_id}/…` 不透明 ID，**不要沿用现在的 `output/课程名/时间_标题`**，
  那里既有用户可控字符串拼路径，也有跨用户的同名冲突。

### 7.6 并发与限流

- 每用户同时 1 个活动任务；全局 worker 槽位按 CPU 核数（worker 自己报）。
- 服务端是 I/O 密集：100 个并发 LLM 流 ≈ 100 个 asyncio 连接，2 vCPU 的 VPS 够用。
  **但不要用现在这种阻塞 `requests` + 线程**，否则 100 并发就是 100 个线程。
- 配额：单任务 ≤ 4 h 音频、单用户存储 ≤ 200 MB、单日 LLM token 上限。
- LLM 失败：429 指数退避、`context` 超限 → 缩输入重试（现有 `ContextWindowError` 逻辑可复用）。

### 7.7 眼睛阶段怎么跨机器

现在的 `vision.run_eyes` 把"LLM 决策"和"ffmpeg 抽帧 + 写盘"焊在一个函数里（`vision.py:259`）。
拆分方案：

- 服务端跑决策（`llm.eyes_decide` / `observe_frames` / `eyes_summarize`），
  通过 WSS 发 `{"type":"get_frames","points":[t1..t4]}`；
- worker 执行 `extract_frames`，上传 JPEG，回 `{"type":"frames","ids":[...]}`；
- 服务端把图发给视觉模型，继续下一轮。

代价：每轮多一次 100 ms 级往返（≤ 8 轮，可忽略）；收益：视频只存在于用户机器。
注意 worker 必须保留视频直到 `eyes` 结束——这意味着任务期间用户不能删文件，
需要在 UI 里说明。

### 7.8 失败与降级

| 场景 | 行为 |
|---|---|
| worker 掉线 | job 停在 `transcribing`，lease 过期后回 `queued`；UI 显示"等待本机上线" |
| 用户合盖/断网 | 同上；重连后从 `max(idx)+1` 继续 |
| LLM key 失效 | job 失败，提示"key 无效/欠费"，文字稿保留可重跑 final_pass |
| LLM 超时/截断 | 保留已出正文，标记 `finish_reason`，允许重跑单块 |
| ASR 报错单块 | 该块重试 1 次；仍失败则跳过并标记空洞，不整单失败 |
| 服务端重启 | job 状态在 DB，worker 重连后自动续租 |

## 9. 安全与合规

### 9.1 威胁模型

| 威胁 | A/D 下的后果 | B/C 下的后果 | 措施 |
|---|---|---|---|
| 数据库泄露 | 全站 PKU 密码 | 站点口令 hash + 文字稿 | 加密、最小化、保留期 |
| 凭据预言机 | 可批量试学号密码 | 无 | 不做公开注册、限流、验证码 |
| IDOR 越权 | 看别人课堂内容 | 同 | 每个查询强制 `user_id` 过滤 |
| SSRF | 可打内网 | 无（在用户机） | URL 白名单 |
| worker 伪造文本 | — | 只污染自己的稿 | 不信任 worker 文本做安全判断 |
| 资源耗尽 | 大视频/长任务 | 同 | 配额、时长上限、并发上限 |
| 日志泄露 | 密码/Cookie 进日志 | 课堂内容进日志 | 结构化日志 + 字段白名单 |
| 提示词注入 | 重述被污染 | 同 | 无工具调用，影响有限；输出转义 |
| XSS | 前端渲染 `retell.md` | 同 | Markdown sanitize、CSP |

### 9.2 合规清单

- 明示：数据用途、保留期、删除方式；首次使用单独勾选同意。
- 最小化：服务端不存视频/音频（B）；A/D 至少只存音频且任务结束即删。
- 用户权利：导出、删除账号及其全部产物（7 天内完成）。
- 不对外分享：每个产物 URL 都是签名短链，禁止公开索引。
- 版权提示保留在 UI 与产物页。
- 上线前向学校相关部门确认"代用户访问教学网"是否被允许——这是**非技术前置条件**。

### 9.3 运维

- 主密钥（加密 LLM key 用）放环境变量/KMS，不进代码库；支持轮换（`key_version`）。
- 备份加密；审计日志保留 90 天，只记事件不记内容。
- 关闭崩溃转储（`ulimit -c 0` / Windows WER），异常信息里过滤 `sk-`、`token=`、`auth_data`。

## 13. 需要你拍板的三件事

## 附录 A：接口契约草案

### A.1 ASR 接缝（唯一的跨机器边界）

```python
# asr.py 新增，streaming.py 只改构造处
class AsrBackend(Protocol):
    def transcribe(
        self,
        pcm: np.ndarray,          # mono float32, 16 kHz
        *,
        language: str = "zh",
        beam_size: int = 1,
        initial_prompt: str | None = None,
        vad: bool = True,
    ) -> list[Segment]: ...

class LocalWhisper(AsrBackend):   # 现在 streaming.asr_body 里的逻辑搬进来
    def __init__(self, model: str, threads: int, device: str = "cpu", compute_type: str = "int8"): ...

class RemoteWhisper(AsrBackend):  # 方案 D 才需要；B 不需要
    def __init__(self, channel: "WorkerChannel"): ...
```

方案 B 里 `RemoteWhisper` 不需要存在——worker 直接跑 `LocalWhisper`，
服务端只消费 `chunks`。这是 B 比 D 少一个组件的直接体现。

### A.2 Worker ↔ 服务端消息（WSS）

```jsonc
// 服务端 → worker
{"type":"job.new","job_id":"...","params":{"chunk_seconds":240,"overlap_seconds":5,"eyes":true,"max_shots":8}}
{"type":"get_frames","job_id":"...","points":[1234.0,1567.5]}
{"type":"cancel","job_id":"..."}

// worker → 服务端
{"type":"accepted","job_id":"...","caps":{"threads":8,"model":"small"}}
{"type":"progress","job_id":"...","phase":"downloading","pct":42}
{"type":"chunk","job_id":"...","idx":3,"start":720.0,"end":960.0,"text":"...","segments":[...]}
{"type":"frames","job_id":"...","items":[{"seq":1,"t":1234.0,"sha256":"...","bytes":98304}]}
{"type":"done","job_id":"...","duration_sec":7162.4}
{"type":"error","job_id":"...","stage":"asr","message":"...","retryable":true}
```

约束：单条消息 ≤ 256 KB（chunk 文本约 1–3 千字，足够）；图片走独立 HTTPS 上传；
所有消息都带 `job_id`，服务端按 capability 校验归属。
